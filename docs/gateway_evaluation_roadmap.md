# 网关基建与评测路线

状态：网关与完整质量评测仍在建设中。主项目 `/chat` 已使用 [请求级业务 Graph](graph.md) 编排召回、回答和记忆维护，并以 FastAPI POST SSE 返回事件。当前代码已有 JWT 注册/登录及资源所有权检查，但缺少端到端验收；请求 ID、限流、模型调用层和指标采集仍未实现。负反馈采集、人工审核、隔离运行及逐例基线对比工具见 [反馈回归流程](feedback_regression.md)，真实质量基线仍待建立。`OPENAI_BASE_URL` 只是模型服务地址。[迁移记录](chat_graph_migration.md) 说明 Graph 的已合入范围。

## 能力边界

```text
客户端
  → API 接入层：当前 JWT 认证；请求 ID、请求大小、限流待建
  → FastAPI /chat
  → 聊天业务流程（已合入请求级 Graph）
      → 模型调用层：超时、错误分类、用量统计、可控切换
      → 工具执行层：身份绑定、权限、超时、输出上限
      → PostgreSQL / Milvus
```

API 接入层保护公开入口；模型调用层管理上游模型；工具执行层约束 Agent 可调用的外部能力。三层都可能被称为“网关”，但身份、计费和重试的责任不同。先把服务内的接口、指标和测试做清楚，再决定是否需要独立代理或网关服务。多 worker 部署时，限流必须使用共享状态或部署层能力，不能把单进程内存计数当成全局限流。

## 实施顺序与验收

| 阶段 | 位置与改动 | 验收证据 |
| --- | --- | --- |
| 0. 运行基线 | `api/server.py`、`src/agent/chat_workflow.py`：给 SSE 请求及 Graph 节点关联 request/trace ID，记录阶段、耗时和异常类型 | 能把一次失败定位到接入、召回、模型、工具、记忆写入或日志提交；日志不含密钥和完整用户消息 |
| 1. API 接入层 | `api/`：对当前 JWT 认证 与所有权代码做端到端验收；再限制请求大小、并发与速率，定义 401、429、5xx 及取消行为 | 不同令牌不能越权；限流在目标部署方式下生效；请求 ID 贯穿错误响应与日志 |
| 2. 模型调用层 | `src/agent/`：统一模型构造与配置，给调用设置超时、错误分类和有界重试；记录 provider/model、token 用量及费用估算；模型切换采用明确配置 | 模型超时、429、上游 5xx 均有可测结果；没有重复执行有副作用的工具或记忆写入；费用规则带版本和币种 |
| 3. 工具执行层 | `src/agent/tools.py`：为工具绑定可信身份、白名单、超时、输出大小与错误类型；区分只读和写操作 | 模型无法通过参数切换用户；慢工具不会无限占用请求；失败与截断在 trace 中可见 |
| 4. 评测流水线 | `tests/`、`docs/`：建立带标签的数据集、固定运行命令和版本化报告；比较聊天流程、模型或阈值变更前后的结果 | 同一批样本可重复运行；报告同时给出质量、延迟、用量/费用与失败分布 |

目前不预设某个网关产品，也不预设“多模型自动降级”一定有益。若切换模型，必须先确认工具调用和结构化输出兼容，并用同一评测集比较质量、时延与费用。写入类操作不自动重试，除非先建立幂等键和重复执行测试。

## 第一版指标字典

指标分为线上运行指标与离线质量指标。线上指标只按有限类别聚合（如 route、stage、provider、model、status class）；用户 ID、会话 ID、request ID、原始 URL、提示词和错误文本不能作为指标标签。单次诊断信息放在受控日志或 trace 中。

| 层 | 指标与计算口径 | 用途 |
| --- | --- | --- |
| API | 请求成功率 = 成功请求 / 全部请求；按错误类别统计 401、429、5xx；端到端耗时 p50/p95/p99 | 判断入口是否稳定、是否被限流、尾延迟是否异常 |
| 模型 | 调用成功率、超时率、429 率；调用耗时及 SSE 首 token 耗时；输入/输出 token、按价格版本估算的单请求费用 | 区分上游故障、慢调用和成本变化；首 token 需从现有 SSE 实际事件测量 |
| 业务阶段 / 工具 | 各 Graph 节点耗时、失败数；工具调用次数、成功率、超时率；记忆更新失败率 | 从一次失败定位具体阶段，发现工具循环或写库异常；采集仍待实现 |
| 召回路由 | “是否需要记忆”的 precision、recall、F1；类别命中率；误触发率 | 区分漏召回与多余召回 |
| 检索 | Hit@K、Recall@K、Precision@K；空结果率；跨用户命中数 | 判断返回的记忆是否相关且属于当前用户；相关性需要人工标注 |
| 记忆写入 | `insert` / `replace` / `none` 动作准确率；重复写入率；错误替换数 | 判断长期记忆是否被正确维护 |
| 回答 | 有依据回答比例、事实错误率、任务完成率；按场景统计拒答或承认未知的正确率 | 衡量最终结果；自动评分需抽样人工复核 |

第一版固定样本至少覆盖：无需记忆、必须召回、多个 memory key、旧事实更新、冲突事实、无结果、工具超时、模型错误、跨用户隔离、带指令的恶意记忆。先建立基线再定质量门槛；跨用户泄漏的验收目标是 0。每次报告记录数据集版本、代码版本、模型、提示词版本、检索阈值和价格版本。具体样本数与质量阈值在首轮基线之后确定。

计算时统一口径：路由的 precision = 正确触发 / 全部触发，recall = 正确触发 / 全部应触发；Hit@K 是前 K 条至少包含一条相关记忆的样本比例，Recall@K 是前 K 条找到的相关记忆数 / 样本中全部相关记忆数，Precision@K 是前 K 条相关记忆数 / 实际返回条数。没有相关记忆的样本单独统计误召回，不把分母为 0 的样本硬计入 Recall@K。回答依据与事实错误使用人工标注或带证据的评审标准；LLM Judge 可辅助扩展，但需抽样人工复核。

运行指标可以沿用 [OpenTelemetry 的 HTTP 请求耗时语义](https://opentelemetry.io/docs/specs/semconv/http/http-metrics/)；离线数据集比较与线上监测的区别见 [LangSmith 评测类型](https://docs.langchain.com/langsmith/evaluation-types/)。这些资料提供度量方式，不代表本项目已经接入相应平台。
